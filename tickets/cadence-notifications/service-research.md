# In-app notification inbox service research

Researched 21 November 2026. Prices and limits are public list prices, not quotes; confirm current terms before committing. This is evidence for the service decision, not a decision to adopt a vendor.

## Cadence context

The agreed [event rules](https://github.com/M-Katarzyna/cohort-005-project-km/issues/10) require a new top-level comment to notify its Instructor; replies to notify eligible thread participants; and new lessons to notify currently enrolled Students in a separate course-updates view. Exclude the actor, deduplicate per event and recipient, and exclude people whose only contribution was deleted. Exact lesson publication, lifecycle, access and inbox behavior remain open. Cadence uses React 19, React Router, Drizzle and SQLite ([package.json](../../package.json), [schema](../../app/db/schema.ts)). Comments have parent links and soft deletion; enrollments are persisted locally. A provider does not inherently know these domain rules or current access rights.

A tab, toast, push alert or marketing in-app message alone is not the required persistent, recipient-specific inbox. The three listed services explicitly offer an inbox/feed; email or push can be evaluated later and are not initial implementation scope.

## Common integration and operational consequences

- **Recipients remain a Cadence responsibility.** Compute eligible recipients using current domain data, exclude actor and deduplicate. Each eligible recipient contributes to the volume: 100 new lessons each reaching 100 Students means up to 10,000 recipient notifications, before comments. This is not necessarily 10,000 billable units for every provider; verify each meter and batching model.
- **Reliable writes need a boundary.** An external API call cannot participate in the SQLite transaction. Consider a transactional outbox with a worker/retry process if lost notifications are unacceptable. Use stable event/recipient keys; vendor retry idempotency windows may be shorter than the desired guarantee. Provider acceptance is not proof that the user saw the notification. A local solution can atomically store the domain change and inbox records, subject to the same database transaction.
- **Privacy and stale content need explicit design.** Provider authentication protects the recipient's feed, but does not automatically re-check enrollment or comment access. Decide whether notification payloads may contain comment text, how removed content is handled, and whether links reauthorize against Cadence. Check provider deletion, retention, export, region, data processing terms, outage behavior and lock-in before selecting. Keep secrets on the server.
- **Initial view separation is plausible, not yet proven.** Novu advertises tabs and Knock supports workflow-category filters. Courier's SDK supports custom feeds, but precise segmentation and counts for the agreed UI require a small proof of concept. Verify unread counts, routing/deep links, accessibility, React Router/SSR compatibility and brand customization for the selected candidate.
- **External channels are a separate decision.** A persisted inbox is useful after return but cannot itself bring someone back while they are away. All three advertise additional channels; whether Cadence needs reminders and how they should behave is unresolved. Channel provider fees may be additional.
